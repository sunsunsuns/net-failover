# 测试报告（实测数据）

> 测试日期：2026-10-31　｜　版本：net-failover v1.0.0
> 测试机：Wheeltec 机器人（Ubuntu 22.04.5 LTS，kernel 6.1.83，aarch64，8 核）

## 测试环境

| 项 | 值 |
|---|---|
| 有线 | `eth0`，DHCP `192.168.3.199/24`，网关 `192.168.3.1`，100 Mb/s |
| WiFi | `wlan0`，`192.168.3.129/24`，网关 `192.168.3.1` |
| 4G | `enx020c29a39b6d`（Quectel，USB 网卡），`192.168.43.100/24`，网关 `192.168.43.1`，出口公网 IP `114.254.10.48`（联通）|
| 叠加网络 | ZeroTier，`ztefxoz7me`，`10.209.251.153` |
| 配置 | `strikes_down=3`、`strikes_up=3`、`cooldown=10s`、`interval=1.5s`、`timeout=1.5s` |
| 探测目标 | `223.5.5.5:443`、`119.29.29.29:443`（TCP）|

## 测试方法

`tests/switch-test.py`：按链路优先级顺序，用 `nmcli device disconnect/connect` 真实
断开/恢复网卡，同时以 20 Hz 探测互联网可达性（TCP 连接），记录：

- **路由切换**：从动作发生到 `metric 50` 的默认路由指向期望网卡的时间；
- **断流**：从动作发生到 TCP 探测重新成功的时间（用户真实感受到的中断）。

## 结果（正式测试，打包版本）

| 场景 | 路由切换 | 断流 |
|---|---|---|
| 断开有线 `eth0` → 切到 WiFi `wlan0` | 1.13 s | **0.32 s** |
| 断开 WiFi `wlan0` → 切到 4G | 0.60 s | **0.20 s** |
| 恢复有线 `eth0` → 升回有线 | 6.29 s | 2.24 s |
| 恢复 WiFi `wlan0` → 保持有线 | 0.46 s | 0.46 s |

一次完整的原始结果：[`tests/reports/switch-report.json`](../tests/reports/switch-report.json)

## 结果（开发期同场景复测，验证稳定性）

| 场景 | 路由切换 | 断流 |
|---|---|---|
| 拔网线 → WiFi | 2.03 s | 0.06 s |
| 断 WiFi → 4G | 0.43 s | 2.21 s |
| 插回网线 → 有线 | 8.89 s | 0.12 s |
| 恢复 WiFi → 保持有线 | 0.49 s | 0.06 s |

## 结论

1. **链路消失时业务几乎无感**：备份路由常驻，内核在毫秒级改道，断流 0.06~0.46 s。
2. **"升回"比"降级"慢**（6~9 s），这是刻意的：升回要连续 3 次成功 + 10 s 冷却，
   防止链路抖动导致来回翻；这段时间流量由低优先级链路承载，业务不中断。
3. **最坏情况（WiFi 整条消失、只剩 4G）** 断流约 0.2~2.2 s，取决于探测周期落在哪一相位。
4. 4G 上 `ping` 100% 丢包但 `curl`/TCP 正常，所以健康判断全部走 TCP。

## 信号阈值验证（dry-run，v1.1.0）

`dry_run = true` 下把阈值临时调到 `rssi_down=-30 / rssi_up=-20`（当时实测信号 -41 dBm，
即"很差"），守护进程给出正确决策且未改动真实路由：

```
22:53:37 [dry-run] ip -4 route replace default via 192.168.43.1 dev enx020c29a39b6d metric 50
22:53:37 切换 -> enx020c29a39b6d (gw=192.168.43.1) [原链路失败/信号差]
实际路由：default via 192.168.3.1 dev wlan0 metric 50   ← 未被 dry-run 改动
```

恢复正式阈值 `rssi_down=-75 / rssi_up=-65` 后，-41 dBm 远高于门限，WiFi 保持为主出口。

## 信号阈值实切验证（真实切换，v1.1.0）

把阈值临时调到 `rssi_down=-20 / rssi_up=-10`（当时信号 -46 dBm，判定为"很差"），
再恢复 `-75 / -65`，两次都是真实改路由：

| 场景 | 实测 |
|---|---|
| WiFi(-46 dBm) → 4G（信号低于阈值主动切走） | **9.3 s** |
| 4G → WiFi（阈值恢复、信号合格） | **12.9 s** |

日志：

```
22:56:11 切换 wlan0 @-46dBm -> enx020c29a39b6d [原链路失败/信号差] (gw=192.168.43.1)
22:56:38 更高优先级恢复：enx020c29a39b6d -> wlan0 @-48dBm (gw=192.168.3.1)
```

## 已知限制

- 切换会改变出口源 IP，**正在进行的长连接会断一次重连**（TCP 四元组变化）。
  这与手机/笔记本换网的现象一致，不是本项目的 bug。
- 4G 上的 ICMP 被运营商拦截，不能用 `ping` 做验收。

## 复现

```sh
sudo ./install.sh
sudo ./tests/switch-test.py --yes --json /tmp/report.json
```

测试会真实断开网卡，**会短暂断网**，请勿在远程会话的关键操作期间运行。
